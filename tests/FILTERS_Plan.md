`-42` interprets stored `0x03D6` as signed two's complement. Hardware establishes RGB order and row-major mixing; diagonal 256 behaves as identity. Factory sign-extended negatives and row sums 255/256 now strongly support signed Q8 (details below); exact rounding/clipping remain unverified. Build 06 supports signed RGB offsets, but units and blue-shadow noise remain unresolved. The writer packs **columns** into `0xB0E4/E8/EC` at bits `0,10,20`; offsets go to `0xB0F0` at the same positions. A zero matrix pointer restores baseline, not identity.

### 17-byte curve

Writer `0x4EB74` packs `p[0..5]` into `0xB168`, `p[6..11]` into `0xB16C`, and `p[12..16]` into `0xB170`, consecutively in 5-bit fields. Every value is `p[i] & 31`; values above 31 wrap rather than clamp. Only 17 bytes are consumed; alignment padding is not part of the curve.

**Round-1 hardware confirms saturation strength:** flat 0 gives grayscale; 8 reduces saturation, 16 slightly increases it, and 31 strongly increases it relative to Normal. Low/middle/high index bands retain color in bright/middle/dark regions respectively. This supports a brightness-dependent axis, but does not distinguish luminance from individual-channel intensity or establish exact boundaries/interpolation. The original all-zero example `1F` also changes a separate tone curve, so it was insufficient evidence alone. Baseline adaptive updater `0x58330` scales all 17 entries by a shared gain divided by 16; that divisor does not prove p=16 is physical unity. Records `81660/81688` are byte-identical.

### 88-byte record and the extra `1F` stage

Record `A3D8` is copied from RAM address `0x020075D8` and contains 22 little-endian 32-bit words. Writer `0x4E1D0` consumes only words **0..12** in fixed effect mode:

| Words | Value | Destination / established use |
| --- | --- | --- |
| `0,1,2,3` | `255,128,200,128` | Low bytes to `0xB15C` bits `24,8,16,0`, respectively |
| `4..7` | All `64` | Low bytes to `0xB160` bits `0,8,16,24` |
| `8..11` | All `64` | Low bytes to `0xB164` bits `0,8,16,24` |
| `12` | `64` | Low byte to `0xB0FC` bits `11..18` |
| `13..20` | `10,10,16,16,16,16,16,16` | Eight gains used by baseline adaptive routine `0x58184`; not read by the fixed writer |
| `21` | `6` | Adaptive bucket divisor; not read by the fixed writer |

Word 2 is **brightness/exposure-related**: setting `0x16` reaches `0x59260` via `0x49A20`, which can adjust this same `0xB15C[23:16]` field in steps of 16. Round 2 establishes contrast-related behavior at word 0 and color remapping at word 3; word 1 changes primary bands/whitepoint. Their equations and words 4..12 remain unresolved. For `1E`, `B15C=FFC88080`, `B160=B164=40404040`, and `B0FC[18:11]=40` (hex).

**Additional stage for table row `1F`:** loader `0x16A38` reads a 512-byte curve from file `0x8DF20` into RAM `0x02009540`. The `1F`-only branch at `0x59560` sends it through `0x4DD54` to device memory `0x84400`. It contains 256 little-endian 16-bit values, observed range `0..1023`, with crushed shadows and a steep rise. Samples at inputs `0,32,64,96,128,255` are `0,0,307,1005,1020,1023`. The fallback table at `0x8DD20` is exactly `4*x`, but normal mode can restore an adaptive baseline instead. A luminance/contrast curve is strongly suggested, not proven.

### Edge stage

Writer `0x4E6AC` packs two 5x5 kernels into `0xB104..B114` and `0xB118..B128`: five 6-bit coefficients per register, in record order. The first kernel at `81630` has `+1` around its perimeter, zero inside and `-17` at its center (`EF` at `8163C`); its sum is **-1**, not zero. The second kernel at `81614` is all zero. Signed 6-bit interpretation gives range `-32..31`; scaling and clipping remain unverified.

The control word is `B100[15:0] = ((t & 63) << 10) | (4 << 7) | 15`, retaining the upper 16 bits. Thus the `0/20/40` parameter is **6 bits**, beside a fixed 3-bit value 4 and 4-bit value 15. A weak-edge threshold fits the observed noise progression; gain/offset meanings are not excluded. Kernel edits affect all six edge IDs; matrix `8177E` is also shared by grayscale and tinted LUT effects.

## Eight-position cycles and additional effects

For **Normal + seven effects**, patch both instructions and the first seven table entries:

| Offset | Original | Eight-position cycle |
| --- | --- | --- |
| `0x39940` | `19 00 43 BD` (`index > 25`) | `06 00 43 BD` (`index > 6`) |
| `0x39968` | `19 00 60 9C` (reverse wrap to 25) | `06 00 60 9C` (reverse wrap to 6) |
| `0x7C504` | 26 effect IDs | Seven desired IDs; Normal is implicit, not another table entry |

For `N` selected effect IDs, each immediate is `N-1`, giving `N+1` positions including Normal. The helper supports `1..26` effect IDs and clears unused slots in the existing table. Both wrap directions must change; changing just the forward bound leaves Up able to select removed entries.

The processing routine already accepts IDs `01..2C` (44 IDs), including the 18 hidden ones. Exposing them reuses existing processing paths. Adding more than 26 table entries needs another change: `0x7C51E/51F` are only two padding bytes, then a code-pointer table starts at **`0x7C520`**. Do not overwrite it. A larger cycle needs a separately allocated/relocated ID table, its pointer at `0x399A0/399A4`, and both wrap limits updated. New IDs above `2C` additionally need the apply-range guard and four parameter tables extended. This is not necessary for eight custom filters.

The LUT selection switch is hard-coded for IDs `02..18`; `1F` has its separate tone-curve path. The current custom curve/matrix probes use IDs `19,1A,1B,1C,1D,20,21` so those special cases cannot confound them. Each probe has a distinct record pointer: the driver caches active pointers and skips unchanged IDs, so repeatedly selecting the same ID/pointer is not a way to supply different simultaneous presets.

## Bytes, bits and editor labels

## Further instruction tracing

This section records the code evidence available before testing 07/08; the later hardware results below resolve the broad role of the nine controls.

Checked original LE instruction words, rather than relying on Ghidra's SPR expressions. [tools/verify_isp.js](tools/verify_isp.js) executes a focused no-delay OpenRISC subset against the SHA-verified backup. It checks software arithmetic/register writes, not the ASIC's pixel equations; the ROM delay/barrier is stubbed. The model's equations remain hypotheses wherever the CPU only transfers parameters.

### Most uncertain: the nine controls and their adaptation

`58184` is enabled by profile flag bits 21:20 = 2. RAM `0201089C` holds the working profile pointer; `+20` holds brightness mean `M`. Record words start at profile `+6B4`. The exact update is:

```text
bucket = min(7, unsigned(M) / word[21])   // integer division; zero divisor is invalid
gain = word[13 + bucket]                 // full u32, Q4: divisor 16
for i = 4..12:
    temp[i] = low32(word[i] * gain) >>> 4
hardware[i] = temp[i] & 255              // wraps, no saturation to 255
words 0..3 pass through unchanged
```

All nine controls share this gain. For example 64 × 16 / 16 sends 64; 255 × 32 / 16 sends **254**, not 255. High raw bits can participate in the multiplication even though the fixed writer reads only low bytes. This raises certainty about the **numeric group, eight gains, divisor and wrap behavior**, not the nine individual image roles. Hue sectors, brightness bands, spatial/noise controls or ASIC-internal subfields remain unproved. Fixed custom effects set mode 1 and ignore words 13..21; changing those tail words in a fixed effect would be an ineffective calibration.

`586E8` derives `M` from 128 histogram entries at RAM `4260`; `587F4..58824` weights bin positions 0,2,..254. `58888` divides the weighted numerator by count; `588C4..588DC` averages the current mean with the previous mean after initialization and stores it at global `+20`. Profile/exposure-dependent weights mean this is **not an ordinary unweighted RGB average**. A separate ring/window average is at `+1C`; the nine-control updater uses `+20`, not that value or ISO. The separate global `+8` exposure/control index drives other interpolators.

The `58330` saturation updater uses the same `M`: 17 bytes at profile `+784`, eight gain bytes at `+795`, divisor byte at `+79D`. It multiplies each strength by the selected Q4 gain, stores the low byte, then `4EB74` keeps five bits. Both decoded profiles have eight gains of 16 and divisor 6, so that adaptation is identity there. This does not establish physical saturation unity 16 or solve the per-pixel brightness axis.

### Matrix signs, brightness and the remaining color equations

Working profile bases are `91B98` (H63P) and `922D8` (H63S), each `88` bytes before the configuration blocks previously listed. Independent `+6B4` color and `+784` saturation offsets confirm the bases. At `+39C`:

| Profile / matrix file offset | Signed coefficient rows | Row sums / offsets |
| --- | --- | --- |
| H63P / `91F34` | `[362,-204,98] / [-18,233,41] / [0,-157,413]` | `256,256,256`; offsets zero |
| H63S / `92674` | `[501,-205,-41] / [-110,511,-146] / [-86,-170,511]` | `255,255,255`; offsets zero |

Negatives are stored as sign-extended u16 (e.g. -204 = `FF34`), then masked to ten bits. Together with hardware identity 256, boost at 511 and suppression at 512/1023, this strongly supports **signed two's-complement Q8**. Clipping/rounding after multiplication remains ASIC behavior. The editor compares canonical low-ten-bit fields, while these original source words retain sign extension.

`59260` caches baseline word 2 at RAM `020075D4`, initially `FFFFFFFF`. With the actual caller's range 5/step 16 it computes baseline + `(choice-3)*16`. Clamp `53340` uses **unsigned** comparisons: a negative result wraps u32 and selects 255, not zero. Stock baselines 128/136 avoid underflow. It stores profile `+6BC`; the branch at `59310..59314` **skips the immediate B15C write in adaptive mode 2**, where the updater consumes the stored value. Other modes receive the immediate write. A separate sensor path exists when profile `+3FC` is zero.

Words 0/1/3 are transferred as whole low-byte fields by `4E1D0`; no RGB565 unpacking, CPU hue formula, quantizer, or independent flags were found in that path. The adaptive updater leaves them unchanged. This sets a firm limit on decompilation: words 1/3 still require hardware calibration or ASIC documentation. In particular, an 8-bit transfer alone does not prove unsigned gain, signed offset or offset-binary encoding.

### Normal edge processing and tone width

`4E2E0` (Normal) differs from `4E6AC` (fixed effects). Its first four arguments pack `B100[15:10]`, `[9:7]`, `[6:4]`, `[3:0]`. Argument 5 (masked byte) substitutes the first kernel center: unsigned `clamp(31-strength,16,31)` via `53340`; strength >31 underflows and returns 31. The stored center is ignored. Argument 6 is overwritten by an SPR read before use and has no effect in this writer. Fixed effects copy the stored center and write zero to `[6:4]`.

Normal kernel pointers RAM `0201075C/02010758` default to ROM files `7F6A4/7F688`, distinct from fixed-effect kernels `81630/81614`. First template rows are `[-1,-2,-2,-2,-1] / [-2,1,3,1,-2] / [-2,3,20,3,-2]`, then symmetric; second rows `[0,0,1,0,0] / [0,2,4,2,0] / [1,4,24,4,1]`, then symmetric. Signed sums before substitution are 8 and 52; adding the banks with a guessed normalization is not established.

Six eight-byte arrays at profile `+710/+718/+720/+728/+730/+738` feed arguments in order **3,0,1,2,4,5**. `57D30` interpolates with the separate exposure/control index, not `M`. Stored mode-1 endpoint arguments are H63P `[5,1,1,1,10,0]` (center 21), H63S `[16,1,1,0,5,0]` (center 26). These are static references; runtime settings can change them. No additional kernel hardware test is required by this batch.

Tone writer `4DD54` sends 512 bytes through generic copy `5544C` to device `84400`; it does not mask each u16 to ten bits. Original tables use 0..1023, but CPU execution preserves values up to `FFFF`. Hardware acceptance of high bits and RGB/luma domain remain unknown. Adjacent `B0FC` fields are independent: another nine-word stage (`4D938`) owns bits 7:0, tone mode owns 10:8, color word 12 owns 18:11. This shared register is not a packed RGB565 pixel.

Analysis only: no compiler changes or new binary. Stock firmware has **seven shared channel-table RAM slots**, five flash-loaded and two generated; these are not five/seven independent RGB filters or a demonstrated processor limit.

LUT loading into RAM is explicit. Other parameters differ: effect records have flash pointers and selected fixed records are copied before their fields are written. The complete program is not simply loaded into RAM: boot copies selected SRAM/main-RAM sections, while main-body callbacks use the `060...` flash mapping.

**G6 RAM evidence:** `55844..55888` clears `02007670..02200000` (end exclusive), called at `55B98`. This strongly supports a configured **2 MiB main-RAM range starting at 02000000**, not a measurement of free space or independent confirmation of physical capacity. Allocator `26760` rounds requests to 64 bytes, walks/splits blocks rooted at `0200A384`, and can fail. Video allocation `295E0..295FC` computes width*height*3/2 and calls it. No peak recording headroom or safe spare block is established.

**Primary-source comparison:** [Spode's HX3302B X9S guide](https://github.com/andrewspode/hx3302b-x9s-camera/blob/main/docs/hardware-and-firmware-guide.md) reports measured 2 MiB RAM, 64 KiB SRAM and flash execution on another firmware/board. Its free-space measurements and addresses cannot be transplanted here. [Sprite_tm's SPI observations](https://spritesmods.com/?art=kid_cam&page=2) support selected boot copies followed by flash instruction fetching. [Puya's P25Q80H specification](https://www.puyasemi.com/gongye/2648.html) identifies **8 Mbit = 1 MiB SPI NOR flash**, not RAM. No authoritative HX3302B datasheet establishing G6 free heap was found.

### Expansion choices

- Reuse the two generated slots: real existing buffers, no extra RAM, but still only seven shared channel tables. Preserve Normal/identity and tone paths.
- **Load only the selected RGB preset:** 768 bytes, then upload through the existing RAM-to-ISP writer. Reuse three slots or allocate one checked scratch buffer. ISP tables persist; no per-pixel/per-frame flash reload is inherently necessary. Requires a verified source-storage plan and changes within existing initialization/selection paths, not implemented here.
- Allocate an expanded bank: eighteen unique custom channel tables plus identity = **4,864 bytes**, versus the current **1,792 bytes**; **3,072 additional bytes**. Use checked allocation rather than extending the fixed bank into tone buffers. Update loader, selector addressing, ownership and reinitialization together. Static evidence alone does not guarantee recording can spare it.

More RAM and more flash storage are separate problems. Keeping modifications inside existing firmware structures also limits where additional source tables can live, even if runtime RAM is available. Changing a count/index alone cannot expand this bank.
